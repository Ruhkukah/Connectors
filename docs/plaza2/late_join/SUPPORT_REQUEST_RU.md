# Черновик обращения в MOEX: поздний запуск FORTS_AGGR20_REPL, SPECTRA 9.9

Адресат: техническая поддержка MOEX. Не отправлено.
Контур: T1, Plaza II / CGate, только чтение. Логин и семизначный раздел следует
добавить непосредственно при отправке по защищенному каналу; в репозиторий они не включены.

18.09.2026 выполнили первичное открытие и повторное открытие слушателя
`FORTS_AGGR20_REPL` с `mode=snapshot+online`. В каждом опыте наблюдение длилось
120 секунд. Оба слушателя успешно открылись, завершили snapshot и перешли ONLINE;
ошибок callback не было. В каждом snapshot зафиксирована committed-запись:

```text
event_id=678984, event_type=1, sess_id=11709, message=session_data_ready
replID=3, replRev=3, replAct=0, server_time=1789662416
transaction_id=16, transaction_row_index=3, observed_before_online=true
```

`server_time` приведено в представлении probe, не как исходные байты типа `t`.
При интерпретации как Unix seconds это `2026-09-17 16:26:56 UTC`, то есть
`2026-09-17 19:26:56 MSK`: вечер предыдущего дня. Декодер применяет timegm к
календарным полям CGate; просим также подтвердить часовую семантику исходного `t`.
Событие предшествует утреннему запуску 18 сентября; наблюдатель следует запускать
до соответствующей смены торгового дня, а не только перед 07:00 следующего утра.
Свежий REFDATA snapshot идентифицировал `sess_id=11709`, инструмент
`isin_id=4519450`, `ALRS-12.26` (`ALZ6`), REFDATA LifeNum `101518051`.
AGGR LifeNum в обоих опытах: `66740`. После ONLINE повторного события типа 1 для
этого sess_id не получено. Это ограниченное наблюдение, а не утверждение, что
повторная публикация невозможна. Свежая корреляция SESSIONSTATE/INSTRUMENTSTATE
этим опытом не доказана.

ONLINE, локальное время UTC: `06:03:51.484865212` и `06:05:51.459836430`;
закрытие: `06:05:51.262980301` и `06:07:51.305282144` соответственно.
По Москве это 09:03:51–09:07:51, 18.09.2026; имя пакета 09:00 не является
фактическим временем открытия слушателя.

Версии: SPECTRA9.9.0, CGate `6.102.0.6118`, P2MQRouter `229.123.0.7233`.
Идентичности бинарного файла, схемы и библиотеки указаны в `external_manifest.json`.
Publisher, command API и order API не использовались.

В руководстве PLAZA II gateway 9.9 одновременно указаны:

1. `Table orders_aggr`, таблица 46, первое примечание: действительность стакана
   обусловлена получением синхронного `session_data_ready` [S1].
2. `Event-sensitive scheme for data synchronizing`, заключительные примечания:
   snapshot не сохраняет межтабличную последовательность, и событие из snapshot
   само по себе не подтверждает согласованность данных в online [S2].

Просим указать точный критерий, ожидаемый при сертификации клиента, который
запускается или перезапускается после публикации текущего `session_data_ready`:

1. Достаточны ли новый завершенный AGGR snapshot, ONLINE, историческая запись
   типа 1 для точно текущего sess_id, свежий REFDATA с тем же sess_id и свежие
   согласованные SESSIONSTATE/INSTRUMENTSTATE? Если да, какие поля, границы
   транзакций, признаки актуальности и проверки поколений обязательны?
2. Если нет, необходимо ли сохранять ранее полученное этим приложением online
   событие? Как повторно проверить такое свидетельство после restart, изменения
   LifeNum/ClearDeleted, смены торгового дня или переподключения? Что делать
   приложению, впервые запущенному в середине дня и не имеющему свидетельства?
3. Существует ли документированный режим replay, запрос или иной барьер, который
   предоставляет эквивалентную синхронизацию без ожидания следующего торгового дня?
   Должен ли сервер повторно публиковать событие при новом открытии?
4. `instrument_state` (таблица 139) содержит isin_id/public_state, но не sess_id.
   Как правильно связать его актуальность с торговым днем и AGGR, учитывая
   независимые потоки? Достаточна ли корреляция sys_events по event_id?
5. Когда T1 публикует событие для следующего торгового дня относительно расписания
   T1? Применим ли тот же критерий в Game, и какие различия необходимо учитывать?

До ответа предлагается только визуализация с явной меткой
`LateJoinCorroboratedSnapshot / provisional`, если все проверки выполнены.
Такой режим не разрешает отправку заявок. Просим отдельно подтвердить смысл
согласованности market data; подтверждение этого критерия не заменяет остальные
проверки торговых прав и готовности клиента.
